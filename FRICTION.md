## Product feedback notes (for the hackathon's required product-feedback answer)

- **Tools/SDKs used**: `@modelcontextprotocol/sdk` (server plus stdio and in-memory transports, `registerTool` with zod schemas) for the MCP surface and for the end-to-end tool tests; `@aws-sdk/client-bedrock-runtime` (Converse) for classification; Node's built-in `node --test` runner rather than a third-party framework, to keep the dependency list honest about what the product needs; `tsx` for running TypeScript directly; `playwright-core` only for turning terminal output into screenshots.
- **What worked**: `registerTool` with zod schemas was straightforward to build thirteen tools against, and `InMemoryTransport.createLinkedPair()` made it possible to test the MCP surface end to end with no process boundary, which is the single best thing in that SDK. Bedrock's Converse API is the right shape for this: one call, a system prompt, a message, and `inferenceConfig` with `temperature: 0`, and it took about ten minutes from install to first verdict. `abortSignal` on `client.send()` made the timeout budget easy to implement correctly.
- **What needs work**: three things, all listed above. `ListFoundationModels` returns models the account cannot invoke, with no per-account invocability field and no pointer to the right inference profile, so the first thing a new Bedrock developer does is fail. `ThrottlingException` carries no `Retry-After` and no quota name, which makes correct backoff guesswork. And Bee's `speaker` field is an untyped string labelled `Unknown` in Bee's own published sample output, with no page saying whether that is temporary or permanent — a real problem for a product whose whole job is telling an instructor's announcement apart from anything else said in the room (row 9). Bee remains the bigger gap of the three: there is still no way past `bee login` without the iOS app, so nothing here has run against a live device.
- **Onboarding**: Bedrock was the smoothest part of this build. Credentials already on the machine, `aws bedrock-runtime converse` from the CLI to sanity-check a model id, then the SDK. The only stumble was the model id, and that is a documentation and API-surface problem rather than an onboarding one. Bee's onboarding is blocked entirely behind a mobile app this environment does not have.
- **Would we build with them again**: yes for the MCP SDK and yes for Bedrock Converse, without hesitation. For Bee: yes for the API shape and the todos/facts/conversations model, which fits this product category well, but only once a server-side integration can authenticate without going through the consumer iOS app first.
